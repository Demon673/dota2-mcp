# Agent Note: Panorama UI control and JavaScript execution

English | [中文](2026-10-26-panorama-ui-control.zh.md)

Status: proposed (bridge and `dota_input` implemented; debugger/multi-root and remaining lifecycle hardening open)

## Problem

The MCP surface can run server Lua and read the VCon console, but it cannot see or operate the client UI. An agent cannot answer what panel sits at a position, what its bounds and visibility are, or how to click a button without a human. That blocks UI work server Lua cannot verify, and it blocks the interaction half of any visual regression loop.

The Panorama Debugger is the engine's own UI inspector: it exposes every panel with its position, class, attributes and styles, and its JavaScript console can run code in the selected panel's context. Combined with the existing VCon channel it could cover most in-game observation and operation without editing the addon. The user's constraint is to keep their input free where possible; a short, explicit focus takeover with restoration is acceptable only when no background path exists.

## Proposal

The execution path is settled first; inspection and OS input follow.

### Layer 0: transient dynamic HUD bridge (verified)

- Server Lua owns the injection point: `CustomUI:DynamicHud_Create(PlayerID, ElementID, LayoutFileName, DialogVariables)` creates a HUD element from a layout, and the client loads that layout and runs its `<scripts>` in a fresh JavaScript context.
- The bridge source lives with the MCP server, not in the addon: a layout XML plus a JavaScript file included through `<scripts><include src="file://{resources}/layout/custom_game/<bridge>/<bridge>.js" /></scripts>`. The official layout documentation describes an inline `<script>` block, but the current on-demand compiler rejects it live: "`<script /> tags within XML files are no longer supported. Please create a separate script file that is included via an `<include />` in the `<scripts />` section.`" The bridge therefore ships two source files, copied and deleted as one unit.
- Provisioning is copy → engine compile → ready → delete (the primary path). Both source files are copied under `{dota2Path}/content/dota_addons/<addon>/panorama/layout/custom_game/<bridge>/`; `DynamicHud_Create` makes the engine compile them on demand into the addon game tree; once `MCP_BRIDGE_READY` arrives on `PanoramaScript`, the source copies and both compiled outputs are deleted. The process-level layout cache keeps the running bridge alive. No addon source remains and no junction is created: through a developer's content-directory junction the files exist in the repository only for the copy/compile/delete window. Re-provision after a Dota restart or a cache loss; a map reload only re-creates the HUD.
- Verified alternatives for a read-only addon or an engine without on-demand source compiling:
  - **Base-game loose resources:** copy the compiled pair under `{dota2Path}/game/dota/panorama/layout/custom_game/<bridge>/`. The loader finds compiled loose resources in the base game, but it does not compile base-game source layout XML.
  - **Addon game-directory junction:** point a directory junction at `{addon}/game/panorama/layout/custom_game/<bridge>` to a directory holding the compiled pair. No Dota install write; the link lives in the addon's game tree. Directory junctions need no administrator rights or Developer Mode, work across local NTFS volumes, require the target directory to exist, and may be left mounted across Dota restarts.
  The layout path must be resource-relative (`file://{resources}/layout/custom_game/<bridge>/<bridge>.xml`). Absolute paths are rejected and any `..` segment is a fatal error.
- `DynamicHud_Create` loads the compiled layout and runs its JS. The JS subscribes to a server custom event and calls `<panel>.RunScriptInPanelContext(d.code)`; `CustomGameEventManager:Send_ServerToAllClients` feeds arbitrary JavaScript. No debugger input, one-slot cache or focus takeover is involved.
- After the layout loads, deleting the source and compiled files does not stop the bridge: the client's process-level layout cache keeps it alive (verified: `13579` after deleting the staged files; a Dota restart clears the cache). The bridge context and listener die on `DynamicHud_Destroy` or a map reload; re-create with `DynamicHud_Create` (the cache may satisfy it) and re-provision after a Dota restart. A cleanup sweep handles a failed provisioning or a killed MCP process so no bridge file persists.
- Fallback A is an addon-resident bridge layout (source in the addon content, compiled on demand by the engine or by `resourcecompiler`), kept for explicit opt-in development and for environments where the transient copy is blocked. Fallback B is the debugger one-slot bootstrap in Layer 1, for when neither bridge is available.

### Bridge protocol and lifecycle

- **Identity and names.** A random 128-bit token, generated once and stored with the daemon state, namespaces every event, element id and resource directory: `d2mcp_<token>_<generation>_exec`, `..._ack`, `..._ping`, `..._pong`; the element id and directory use `d2mcp_<token8>_<generation8>`. The generation hashes the bridge source, protocol version and helper API, so a new bridge revision uses new names and cannot collide with game events, another addon or a cached old layout.
- **Request/ack.** The client bridge answers a ping with a pong and an exec with two acks: `started` before it compiles the code and `done` after it finishes, carrying `{id, phase, ok, result|error, logs}`. The client sends acks with `GameEvents.SendCustomGameEventToServer` (verified live); a server listener registered with `CustomGameEventManager:RegisterListener` stores them in a Lua table and prints a token-prefixed line. The MCP tool matches the id and phase in the console stream; Lua can inspect the table asynchronously.
- **Lua cannot block.** The server Lua VM and the client JavaScript VM are separate; `Send_ServerToAllClients` returns before the client runs. Lua learns the outcome through the listener callback and the ack table; the MCP tool is the component that waits on the console marker and decides whether to rebuild. A synchronous Lua return would require a coroutine/timer and is not needed.
- **Ensure is idempotent.** Before each exec the tool installs the server listener (guarded by a token-named global), pings the bridge and reuses it when the pong matches the generation. Without a pong it tries `DynamicHud_Create` from the process cache; only when that misses does it copy the two source files, let the engine compile, wait for a ping, and delete the source and compiled outputs. Provisioning is serialized by the daemon/shared lock; the state file records the token, generation, Dota process/map key and element id.
- **Invalidation and rebuild.** The state key includes the Dota process start, map, addon and generation. `dota_restart`, a map reload, a Dota crash/restart, `DynamicHud_Destroy` or a failed ping invalidate the client HUD; the next exec reinstalls the listener, tries the cache and provisions if needed. A failed compile or load returns the console error and cleans the transient files.
- **No blind exec retry.** An exec may have side effects. A missing `started` ack means the event did not reach the bridge and is safe to retry; a `started` ack without `done` returns `exec_incomplete` instead of running the code twice. The bridge caches acks by request id for the life of the HUD, so a retried id returns the cached result rather than re-executing.
- **Common JavaScript surface.** The bridge predefines `MCP`: `top`, `select`, `$`, `context`, `locate`, `panel`, `text`, `cls`, `style`, `visible`, `snap`, `log`, `help` (the first slice; `tree`/`click` are planned once their panel APIs are verified). The wrapper runs the submitted code inside a function with a `try/catch` and returns its value automatically, so the model writes short expressions such as `MCP.text('#Label', 'Hi'); return MCP.snap('#Label')` instead of repeating panel lookup and `$.Msg`. The bridge runs in its own dynamic HUD layout context, not the addon's custom UI JS context: addon-defined globals are out of scope, while standard engine globals and methods/properties on reachable panel instances are available. Native `$`/`$.FindChildInContext` resolve only inside the bridge layout; `MCP.select('#id')`/`MCP.$('#id')` search from the outermost panel (`MCP.top()`, measured `DotaHud`) with `FindChildTraverse` plus a bounded child walk, and an optional second panel argument scopes the search; `MCP.panel` and the text/visible/cls/style/snap helpers use that global selector. `MCP.context()` reports the root, top, parent chain, which standard globals exist and the area hints. The shipped surface also includes geometry (`MCP.rect`/`center`/`isVisible`/`panelAt`), world and cursor conversion (`MCP.cursor`/`entitiesAt`/`worldToScreen`/`screenToWorld`), game state (`MCP.units`/`unitInfo`/`selection`/`selectUnit`/`selectAllUnits`/`camera`/`order`), and the background event helpers above; live checks cover a visible panel's geometry, a world-to-screen round-trip, hero selection, a camera state read and a harmless stop order. The helper surface includes `map()` (anchors, labels, current HUD/custom-UI areas), `children(sel)` (one level), `customUi(sel?)` (anchored at `CustomUIRoot`, the most common addon-UI entry) and `hudElements(sel?)` (anchored at `HUDElements`); the anchored searches return null when the anchor or panel is absent instead of falling back to the whole HUD. Background event drivers cover the events the engine can raise without OS input: `focus(sel)`/`blur(sel)` (`SetInputFocus`/`DropInputFocus`), `selectPanel(sel, selected?)` (`TogglePanelSelected`/`SetPanelSelected`), `setValue(sel, value)` (raises `onvaluechanged` on sliders) and `setText(sel, text)` (raises `ontextentrychange` on text entries); `dispatch(event, sel, ...args)` forwards any engine event listed by `dump_panorama_events`, and `on(sel, event, fn)`/`emit(sel, event, ...args)` register and directly invoke handlers attached through the bridge. Live measurement: `SetInputFocus`/`DropInputFocus` raise `onfocus`/`onblur`, `TogglePanelSelected` raises `onselect` when it selects (toggling off may not), and slider value/text-entry text setters raise their change events, all while the game is unfocused. A plain `Button` accepted `SetPanelSelected(panel, true)` but raised no event; `TogglePanelSelected` is the reliable background `onselect` path. `$.DispatchEvent('onactivate')` and every `onmouse*` name are rejected with `Invalid event name`, so button activation and hover still need real input or an addon test hook; `emit` only covers handlers registered through the bridge. The bridge's reach stops at the root of its top-level window: other top-level windows have separate JS contexts, and the live API exposes no `GetRootPanel`/`GetAllPanels`; `DotaHud.GetParent()` is null and `RunScriptInPanelContext` on it from the bridge is rejected for a domain mismatch. Reaching another root needs the debugger or a native path. New UI can be created with `$.CreatePanel('Panel', MCP.top(), '<id>')`, as a sibling of the engine HUD root `Hud`; this does not create another top-level window, and existing engine panels cannot be reparented. Each helper is verified live before it ships; geometry/style helpers depend on the panel API version.
- **Concurrency.** The daemon (or the local fallback) owns one bridge manager, one provisioning lock and one ack router; requests carry a unique id and are correlated by the console marker. Multiple MCP sessions share the bridge; the bridge executes events in order, and the ack cache makes a duplicate id safe. A generation change destroys known old element ids and sweeps only token-named directories.
- **Failure codes.** `bridge_unavailable`, `bridge_compile_failed`, `bridge_ping_timeout`, `exec_not_started`, `exec_incomplete`, `js_error`, `lua_listener_failed`; each error carries the generation, request id and the relevant console lines. A failed cleanup is a warning, not a bridge failure.
- **Testing.** Offline: a fake VCon server covers ensure/reuse/rebuild/timeout/error paths and file staging/cleanup. Live: first create, second reuse, deletion, map reload, Dota restart, `DynamicHud_Destroy`, compile failure, JavaScript exception, concurrent sessions and content-junction repo cleanliness. The client-to-server ack path is already verified with a probe (`MCP_ACK_REPLY 42 1 PONG`).

### Layer 1: debugger-driven inspection

- Open the debugger without a hotkey: `panorama_dispatch_event CreateDebuggerWindow()` creates the `Panorama Debugger` window through the engine's event factory. The window loads `panorama/layout/debugger.xml` and is captured without OCR through `PrintWindow`.
- The debugger's JavaScript console still needs a JavaScript-backed panel selected and typed input while the debugger owns the foreground. Every submission re-runs the first successfully compiled script for the process (one-slot cache), so the console is the fallback, not the primary path.
- Event strings use `Name(args...)` with single-quoted string arguments. Flat names and brace forms fail; `TextEntrySetText('...')` is accepted but changes nothing because `panorama_dispatch_event` creates the event with no creating panel.
- The debugger exposes inspection data only as rendered text. A machine-readable inspection result needs a different channel (clipboard, a debugger log or another engine hook) and stays an open question.

### Layer 2: window and input operations

- Implemented as `dota_input`: `window_info` reports outer/client rectangles, client origin, DPI and foreground state; move/click/down/up/drag/wheel, key press/down/up and Unicode text take client-area coordinates.
- Bounds are checked before input; the tool returns the client geometry, focus/cursor state and the restored flags. The previous foreground window is restored only when `restore_focus:true`; restoring focus in `-tools` mode hides the game window, so the default leaves the game focused, and a requested restoration re-shows the hidden window without activating it.
- Live verification: a probe Button receives a real `onactivate`, hover enter/leave, the native chat TextEntry receives Unicode text and key presses, and the game window remains available after input.

## Measured behavior

Live measurements on a `-dev -tools` session; every claim below is from the running engine unless marked otherwise.

- The debugger is a second top-level `SDL_app` window in the Dota process titled `Panorama Debugger`; it has no child windows.
- `panorama_toggledebugger_mode` is a hidden ConVar whose help reads "Toggledebugger key operation : 0 = open/inspect, 1 = open/close"; setting it did not create or close a window in the live session. The engine's debugger hotkey does: with the `Dota 2` window focused, a synthetic F6 created the `Panorama Debugger` window; `WM_CLOSE` closes it and a later F6 recreates it.
- `panorama_dispatch_event CreateDebuggerWindow()` also creates the debugger: the window appeared with `panorama/layout/debugger.xml (87 refs)` in `panorama_print_cache_status`; `PrintWindow` captured the blank inspector and its JavaScript Console input. No hotkey or game focus is needed to open it.
- The ConVar's two modes behave as the help says. With `1` (open/close), F6 opens a populated inspector whose tree, style pane and context line are live: clicking a tree row changes the selection, the inspect button plus a click on the game's minimap selected `DOTAMinimap#minimap`, and the search and console fields accept typed text. With `0` (open/inspect), F6 opened a blank window that ignored the same clicks and keys. The earlier empty-window observation was this mode, not a broken window.
- Typing into the JavaScript console works only while the debugger window really owns the foreground. Every submitted line is echoed. When the call returns before V8, the echo is followed by `1`; when it executes, the echo is followed by the script's own output and no `1` appears.
- The console executes when the selected panel belongs to a layout that has a JavaScript context. A minimal addon custom UI (a `custom_ui_manifest.xml`, a layout with `<scripts>`, and a JS file) compiled with `resourcecompiler` and loaded in game; `$.Msg("MCP_UI_TEST_LOADED")` reached the `PanoramaScript` channel. After the debugger's inspect click selected `#McpUiTestLabel`, submitting `McpUiTestPing("HELLO123")` ran the function: the label text changed to `PING HELLO123` and `MCP_UI_TEST_PING HELLO123` appeared on `PanoramaScript`. A base-game dashboard layout also supplied a working context, so a JavaScript-backed layout is sufficient; the addon UI was the convenient one under test.
- The first-script bridge is verified end to end. The 109-character first script `$.p=$.GetContextPanel();$.Msg("B");GameEvents.Subscribe("j",function(d){$.p.RunScriptInPanelContext(d.code)})` compiled and ran in the addon custom UI context (console showed `B`) and subscribed to the custom event `j`. The server then sent `CustomGameEventManager:Send_ServerToAllClients('j', { seq = 1, code = 'McpUiTestPing(777)' })` through the existing Lua channel; the listener called the panel method `RunScriptInPanelContext(d.code)`, the engine compiled and ran that code, `MCP_UI_TEST_PING 777` appeared on `PanoramaScript`, and the label text changed to `PING 777` in a non-stale capture. A second event carrying `$.Msg("DIRECT456")` printed `DIRECT456`, so the bridge is repeatable and runs arbitrary JavaScript, not one fixed function.
- The no-debugger path is verified: `CustomUI` is a server-side table (`type(CustomUI) == "table"`) exposing `DynamicHud_Create`, `DynamicHud_Destroy`, `DynamicHud_SetDialogVariables` and `DynamicHud_SetVisible`. `CustomUI:DynamicHud_Create(-1, 'mcp_dyn_bridge', 'file://{resources}/layout/custom_game/mcp_dyn_bridge.xml', {})` made the client load that layout and run its script (`DYN_READY` on `PanoramaScript`); the layout's JS registered a listener for the custom event `k`, and `CustomGameEventManager:Send_ServerToAllClients('k', { seq = 10, code = '$.Msg("DYN_EXEC")' })` executed through `RunScriptInPanelContext` and printed `DYN_EXEC`. No debugger, console input or one-slot cache is involved. The client-to-server feedback path is also verified: `GameEvents.SendCustomGameEventToServer('mcp_ack_reply', { id: 42, ok: 1, payload: 'PONG' })` from the dynamic HUD JS reached a server `CustomGameEventManager:RegisterListener`, which printed `MCP_ACK_REPLY 42 1 PONG`; the client printed `MCP_ACK_RECV 42`.
- The bridge's JavaScript context is its own dynamic HUD layout, not the addon's custom UI scope: `MCP.context()` reported the parent chain `<bridge> -> CustomHudElements -> CustomUIRoot -> Hud -> DotaHud`, with `top_id` `DotaHud`; `Game`, `GameEvents`, `GameUI`, `Players` and `Entities` are objects, while `CustomUI` is undefined (server-only). Native `$('#Hud')` returned null while `$('#<bridge element>')` found the bridge root, so `$` resolves only in the bridge layout. From `DotaHud`, `FindChildTraverse` found `Hud`, `HUDElements`, `CustomUIRoot` and `minimap_container`; `minimap_container.FindChildTraverse('minimap')` found the deep child `minimap`. `DOTAMinimap` is the debugger's panel type label, not the id exposed to JavaScript, which is why the earlier `MCP.locate('DOTAMinimap')` failed. The same top search found the bridge root and returned null for a missing id; passing the bridge root as the scope excluded `Hud`. `$.CreatePanel('Panel', MCP.top(), 'McpTopProbe')` created a panel whose parent is `DotaHud`; `DeleteAsync(0)` did not remove it while the game window was unfocused, and the panel disappeared only after forcing `r_always_render_all_windows 1`, so runtime UI deletion waits for a client render frame; the probe panels were then cleaned up and the cvar restored to false. The top-level boundary was measured too: `DotaHud.GetParent()` returned null; `RunScriptInPanelContext` on `DotaHud` from the bridge threw `RunScriptInPanelContext must be called from a context with a domain that matches this panel`; the live `$` API exposed no root accessor; and `MCP.select('#Dashboard')`/`#DashboardCenter` returned null from the HUD root while dashboard layouts remained in the layout cache. The bridge therefore covers the HUD top-level window, not its sibling windows. `MCP.map()` returned the path `DotaHud > Hud > { HUDElements | CustomUIRoot > CustomHudElements }`, 10 custom-UI areas including `CustomUI` and the `CustomUIContainer_*` set, 38 engine-HUD widgets including `topbar`, `minimap_container` and `shop`, plus labels; `MCP.customUi('#CustomHudElements')` found the bridge container, `MCP.customUi('#HUDElements')` returned null, `MCP.hudElements('#minimap_container')` found the minimap container, and `MCP.children('#CustomUIRoot')` returned its 10 children. Addon-defined globals are out of scope; methods and properties on reachable panel instances are available.
- The bridge layout is a minimal XML with a `<scripts>` include and a root panel without an `id`, plus its JS. A root panel carrying an `id` is rejected with "Found root panel with 'id' attribute, which is not permitted".
- The layout loader rejects an absolute layout path with `FixupResourceName: Illegal full path passed in (...)` and a failed load. Any `..` segment is fatal: `FATAL ERROR: Error loading ...: paths to layout files cannot contain '..'` terminates the game. Binary strings show the same rule for CSS and UI-script includes. Never probe `..` in a live session.
- The loader accepts compiled loose layouts from the base-game root: a compiled pair copied to `{dota2Path}/game/dota/panorama/layout/custom_game/...` loaded and ran (`EXT_RC_LOADED`). A source XML in the same base-game tree did not compile on demand; the loader looked for the `.vxml_c` and failed.
- The loader also follows directory links in the addon game tree: both a directory symbolic link and a directory junction at `{addon}/game/panorama/layout/custom_game/<name>` pointing to an external directory of compiled files loaded their layout (`EXT_GDIR_LOADED`). A mounted junction is persistent: after a full Dota restart, the `mcp_bridge` junction still loaded the compiled pair from `%TEMP%` and executed the fed `$.Msg(445566)` (`MCP_BRIDGE_READY`). Junctions need no administrator rights or Developer Mode, work across local NTFS volumes (addon on D:, target on C:), and require the target directory to exist first; a dangling target fails to create. Git reports the mounted link as an untracked directory (`?? game/panorama/`), so it must not be committed.
- Source files in the addon content tree are compiled on demand: symlinked `mcp_sym.xml`/`.js` in `content/panorama/layout/custom_game/` compiled on load and ran (`EXT_SYM_LOADED`), and a plain source copy compiled the same way (`EXT_SRC_LOADED`). A directory junction in the content tree was not traversed for source lookup; that load failed without an on-demand compile. The official Panorama JavaScript documentation allows an inline `<script>` block in a layout XML (auto-wrapped in CDATA), and several installed addons contain one, but the current on-demand compiler rejects it live: `mcp_inline.xml(2,3): RESOURCE COMPILE ERROR: <script /> tags within XML files are no longer supported. Please create a separate script file that is included via an <include /> in the <scripts /> section.`; `CreateElement` then failed to load the layout. The current compiler requires the XML plus a separate included JS file.
- `resourcecompiler` compiled a temporary addon's layout and JS to `.vxml_c`/`.vjs_c` only when the input path was spelled under `content/dota_addons/<addon>`; temporary junctions in the Dota install made that path valid. The output landed in the temporary game tree. A plain temp source path failed with `File "" doesn't exist!`.
- The external bridge is verified end to end: the compiled pair was staged in the base game, `DynamicHud_Create` printed `MCP_BRIDGE_READY`, and a server event fed `$.Msg(24680)` which printed `24680` after a full Dota restart. Deleting the staged files kept the running bridge working (`13579`); `DynamicHud_Destroy` stopped the listener; re-creating the HUD from cache printed `MCP_BRIDGE_READY` and accepted `77777`, all with no staged files left. The full copy → engine compile → ready → delete cycle is verified: the source pair copied through the test addon's content-directory junction compiled into its game tree, the bridge executed `$.Msg(12345)`, deleting both source and compiled outputs kept it alive, and `$.Msg(13579)` still executed; the test repository's git status was unchanged. A map reload then destroyed the HUD and the next exec rebuilt it (`rebuilt:true`, result `42`). A created Panel round-tripped text/visible/style (`hello`, `false`, `10.0px`), and a syntax error returned `js_error` with `RunScriptInPanelContext was unable to compile provided script`.
- The bridge's lifetime is otherwise the same as the addon-resident bridge: deleting sources and compiled outputs does not affect the running bridge, because the client keeps the loaded layout in the process; the in-memory cache is emptied by a game restart.
- `eval` and code generation from strings are blocked in the Panorama V8 context: the first bridge attempt (an `eval(d.code)` listener) produced `EvalError: Code generation from strings disallowed for this context`. `RunScriptInPanelContext` is the engine-side compile-and-run entry that works.
- Panels from layouts without a JavaScript context (the minimap in `hud_reborn.xml`, the spectator listener) still get no context: `GetContextForPanel` returns null, `RunScript` returns before V8, and the console only acknowledges the submit. The earlier "console never executes" conclusion was measured entirely on these panels.
- The console caches the first successfully compiled script for the whole client process. Every later submission — different text, different panel, different context — re-runs that first script instead of compiling the new input; the cache key is the fixed source name `JSConsoleInput`. A full map reload created a new context (the debugger's context pointer changed and the layout's `$.Msg` re-ran), yet the cached script still ran; in a dashboard context it produced `Uncaught ReferenceError: McpUiTestPing is not defined`.
- Closing and reopening the debugger window, `hud_reloadscheme`, and a map reload do not clear the cache. Only restarting the Dota process does. The console's command list exposes no reset: `find panorama`, `find reload`, `find lrucache`, `find v8` and `find script` contain no script-cache command, and `lrucache_flush` covers only the asset-thumbnail and word-filter caches.
- Runtime failures print in the debugger and on the engine console: `JS Exception! *** Skipping rest of script ***`, the `JSConsoleInput` source name and line, the script text, and the stack; `PanoramaScript` carries the same text at verbosity 3. Compile failures were not produced in a JavaScript-backed context, so their output is unverified.
- The console input is a Panorama TextEntry, not a normal edit control. Clipboard paste works when the window is foreground; `Ctrl+A` does not select the existing text (pastes append). The TextEntry drops long pastes: a 113-character script landed and a 133-character script was silently dropped, so the practical limit is near 128 characters; the 109-character bridge fits. Multi-chunk pastes are unreliable. The window can open with an empty tree and style pane; opening it while the game window keeps the foreground, selecting a panel with the inspect click, and closing and reopening once produces a populated inspector.
- The debugger's tree and style pane can be empty even in mode `1` when the window was opened while focus moved away during initialization; the same window retains a selection made earlier, and a close/reopen populates it.
- The `1` acknowledgment is not an execution result; successful execution is observed through side effects (panel changes) and `$.Msg` output on `PanoramaScript`.
- Posted `WM_CHAR` and `SendMessageTimeout` text are ignored by the window. `SendKeys`/`SendInput` works once the window is foreground; the foreground sequence `AttachThreadInput` + `BringWindowToTop` + `SetForegroundWindow` + `ShowWindow` succeeds from a helper process.
- `panorama_dump_symbols <type>` works live: `0` prints 14,471 event symbols (`MoveUp`, `JSScheduledFunction`, `ReloadChangedUIFiles`, ...) and `1` prints 581 file symbols; every other type value prints the usage line.
- `panorama_print_cache_status` prints the layout cache summary (267 layouts with refcounts). `panorama_print_render_tree` is a string ConVar — "Print the RenderOperation_t tree for the given root window; set to * to print all" — but the live values `*`, `Dota` and `dota2` printed nothing.
- `panorama_dispatch_event` creates an event from the argument string and dispatches it with no creating panel. The accepted syntax is `EventName(args...)`; the parser requires the `(`, looks up the event name in its symbol table, and splits arguments on commas outside nested parentheses, with single-quoted strings. `CreateDebuggerWindow()` opened the debugger; flat names, brace forms and `TextEntrySetText(...)` without a creating panel did not produce an observable event effect.
- `cl_script_reload_code <name>` executes a client VScript Lua file from `{addon}/game/scripts/vscripts/` (`CL_VM_OK`). An external path outside that mount fails with "type does not match VM type"; a missing extension is searched with `.lua`. Client VScript exposes 154 functions, including `SendToConsole` and `DoIncludeScript`, but no Panorama or JavaScript entry.

## Engine surface

- The engine binary exposes `RunScriptInPanelContext(script)` as a panel method, with the constraint that the caller's domain must match the panel's, and logs `%s#%s - script run in context`. The debugger console calls `CUIEngine::RunScript`; the verified bridge calls the panel method from JavaScript instead (`<panel>.RunScriptInPanelContext(code)`), which compiles and runs the code in that panel's context and is the only working path around the blocked `eval`.
- `CDOTA_CustomUIManager` (global `CustomUI`) is the server-side injection surface: its four `DynamicHud_*` methods create, destroy, update variables on and toggle visibility of a client HUD element loaded from a layout file. `DynamicHud_Create` is what makes the client load the bridge layout and run its JS.
- `CDOTA_CustomUI_Root::CreateElement` resolves `file://{resources}/layout/...` through the resource system: the addon game tree and the base-game `game/dota` root are searched for compiled resources; loose compiled files in the base game are accepted, and addon content source is compiled on demand. The layout and its script must be separate files; the current compiler rejects an inline `<script />` with `<script /> tags within XML files are no longer supported. Please create a separate script file that is included via an <include /> in the <scripts /> section.` Absolute paths are rejected, and any `..` in layout, CSS or UI-script paths is fatal.
- `panorama_dispatch_event` calls `CUIEngine` vtable slot `+0x330` (`CreateEventFromString`) with a null creating panel, then dispatches the created event through vtable slot `+0x178`. The parser reads the event name up to the first `(`, looks it up in a symbol table, then splits arguments on top-level commas, handling nested parentheses and single-quoted strings.
- The debugger's console submit lives in client.dll (`CPanoramaClientDebugger`), not panorama.dll: a native `TextEntrySubmit` handler for the `JSConsoleInput` TextEntry calls `CUIEngine::RunScript (compile+run)` — UIEngine vtable slot `+0x268` — with the selected panel's context, the text, and the source name `JSConsoleInput`. That fixed source name is also the cache key: the first compiled script is reused for every later submit, so the console runs one script per process.
- `CUIEngine::RunScript` resolves a V8 context through `GetContextForPanel` and returns silently when it gets none (layouts without a JavaScript context). For a JavaScript-backed layout it compiles and runs the text. Only `RunFunction` prints a result (`=> value`) through `JSConsoleOutput`; the console's `RunScript` path prints no return value, so results are observed through side effects and `$.Msg`. `GetContextForPanel` either reuses a context cached per panel or creates a new V8 context, and has an early null path for panels with particular flags.
- `CUIEngine::CompileScript` has exactly three resolved callers: `RunScriptInPanelContext`, the script-string form of `SetPanelEvent`, and a multi-statement runner that splits on `;` and is reached through a vtable. `RunScript (pre-compiled)` has two: the panel event dispatcher (event kind 3) and `RunScriptInPanelContext`. No other native script-compile path exists in `panorama.dll`.
- Binary strings also expose `JSConsoleOutput`, `ToggleDebugger` and `CreateDebuggerWindow`; they are registered Panorama UI event schemas. `CreateDebuggerWindow` is dispatchable through `panorama_dispatch_event`; the debugger hotkey is the `CDebuggerInputHandler` class, which binds `PanoramaDebuggerHotkey`.
- The debugger layout's JavaScript handlers (`PrevSearch`, `UpdateJSConsolePriorHistory`) exist only as event expressions in `panorama/layout/debugger.vxml_c`; the native submit handler and the `JSConsoleInput`/`JSConsoleText` bindings are compiled into client.dll.
- `GameEvents.SendCustomGameEventToServer` is verified in a JavaScript-backed dynamic HUD context: a server `CustomGameEventManager:RegisterListener` received its payload. `Game.ServerCmd` and `Game.AddCommand` are listed by a third-party API snapshot and were only exercised in a null context; treat them as unverified. The live TypeScript declaration dump also lists `Panel.RunScriptInPanelContext`, `Panel.BLoadLayout`, `$.CreatePanel`, `$.DispatchEvent` and `Game.AddCommand`.

## Open questions

- The primary runtime variant is the copy → engine compile → ready → delete cycle; it is verified live, including through a developer's content-directory junction (the test repository's git status returned to its prior state). The recorded element id now drives old-generation HUD cleanup. Remaining: a failed-provisioning sweep after a kill, a measured full Dota process restart, and large-result/chunk edge cases.
- The process layout cache is keyed by resource path. If a later MCP version ships a different bridge source at the same path, the cache may serve the old layout; decide whether to version the bridge directory or accept one bridge revision per game process.
- Re-creating the HUD after a map reload is measured (`rebuilt:true`, result `42`); a full Dota process restart and a cache eviction still need the same live matrix. The bridge is identified by ping, not the one-time `MCP_BRIDGE_READY` marker.
- The server event carries the code, so the fed JavaScript is bounded by the `dota_run_lua` statement limit (about 510 bytes after wrapping, roughly 300 bytes of Lua). How should longer code travel: split across events with client-side reassembly, a file the client reads, or a dedicated bridge?
- Can `TextEntrySetText` or `TextEntrySubmit` be dispatched to a specific panel without focus? `panorama_dispatch_event` creates the event with no creating panel, and the event is a no-op for the debugger input in that form; another event route or a native submit path would remove the focus/typing step from the fallback.
- Can the debugger's rendered inspection data (tree, style pane, context line) be read back machine-readably, through the clipboard or an engine hook, without OCR?
- Can the console be operated without taking the foreground? Posted input is ignored, so the current answer is no.

## Alternatives considered

- **Transient addon-content copy of the bridge.** The primary path: keep the bridge source with the MCP server, copy the XML and its included JS into the addon content, let the engine compile them on demand, load the layout with `DynamicHud_Create`, feed JavaScript through a server event, and delete the source copies and both compiled outputs after `MCP_BRIDGE_READY`. No junction and no persistent addon file; through a developer's content-directory junction the files exist in the repository only for the copy/compile/delete window. The full cycle is verified live: the source pair compiled on demand through the test addon's content junction, the bridge executed `$.Msg(12345)`, deletion kept it alive (`$.Msg(13579)`), and the repository's git status was unchanged. For a read-only addon or a non-compiling engine, the compiled pair can be staged in the base game or behind an addon game-directory junction instead.
- **Addon-resident dynamic HUD bridge.** Verified end to end; kept as the opt-in fallback: the server creates a HUD element from a compiled bridge layout in the addon, the layout's JS registers the listener, and the same event feed runs arbitrary code through `RunScriptInPanelContext`. The cost is a bridge layout in the addon.
- **Bootstrap a persistent JavaScript bridge through the debugger's one allowed script.** Verified end to end: the first script subscribes to a server-delivered event and calls `RunScriptInPanelContext`; the server feeds code through `CustomGameEventManager:Send_ServerToAllClients`. Kept as the no-file fallback because the one-slot cache, the JavaScript-backed panel requirement and the TextEntry make it fragile.
- **Open the debugger with `panorama_dispatch_event CreateDebuggerWindow()` instead of F6.** Verified: it removes the hotkey and the game-focus requirement from opening the inspector, but not the console's foreground/typing requirement.
- **Start with OS-level window and click automation.** It gives coordinates and clicks but no panel identity, attributes or styles, and it necessarily occupies the input device. Kept as Layer 2 and as the fallback.
- **Inject a JavaScript bridge by writing files into the user's addon.** Rejected for the product: it edits source we do not own, requires a reload, and contradicts the contract that addon files belong to the developer. The live experiments added test files to the test addon only, as fixtures.
- **Treat the console's trailing `1` as evidence of execution.** Rejected: the `1` is the acknowledgment for a call that returned before V8; successful execution shows the script's own output and side effects.
- **Read the debugger's output pane by screenshot and OCR.** Rejected for the first slice: fragile, slow, and unnecessary if a console or event channel can carry the result.

## Acceptance criteria

- The measured primary path is recorded: the bridge source stored with the MCP server is copied into the addon content, compiled on demand, loaded by `CustomUI:DynamicHud_Create`, runs its JS, registers a listener and executes arbitrary code delivered by a server event through `RunScriptInPanelContext`; the source and compiled outputs are deleted after `MCP_BRIDGE_READY`, leaving no bridge file. The addon-resident bridge and the debugger one-slot bootstrap are fallbacks. The note claims inspection plus the verified bridge, not a general one-call evaluation from any panel.
- Panel inspection returns id, class, position, size and visibility for a requested panel or subtree from the live UI.
- Interactive operations take focus only for the bounded action; `dota_input` keeps the game foreground by default and restores the previous window only on request; out-of-bounds coordinates fail before focus with the geometry in the error.
- Every engine API used is verified live before it is hardcoded; offline tests cover coordinate conversion, bounds rejection and result parsing.
- The note, the tool contract and the bilingual docs ship together; live evidence moves into the implemented note.

## Risks

- The primary variant writes the two source files into the addon content and the engine writes both compiled outputs into the addon game tree. A killed MCP process between copy and delete can leave them behind, and through a developer's content-directory junction they appear as untracked repository files; the tool must use a dedicated bridge directory, delete only files it wrote, and sweep a failed provisioning on the next daemon start or client disconnect. The base-game and addon-junction fallbacks retain their own footprint: base-game staging writes loose compiled resources into the Dota install (explicit opt-in, removed after load, not for online or ranked play; Steam integrity and anti-cheat behavior unverified), and the mounted junction is visible to git as an untracked directory, must not be committed, and must be detected and re-provisioned when its target is cleaned.
- The primary flow removes the build-specific compiled-pair cache problem by compiling from source each provisioning, but it depends on the engine's on-demand source compiler (available in the `-tools` development session). If a build drops that compiler, the tool must fall back to a compiled pair or the addon-resident bridge. The process layout cache can also mask a changed bridge source at the same path, so a bridge revision needs a new path or a fresh game process.
- The layout loader treats any `..` segment as a fatal error. Never probe traversal in a live session; a failed absolute path is non-fatal, but `..` exits the game.
- The bridge depends on the undocumented `CDOTA_CustomUIManager` API and on `RunScriptInPanelContext`; both can change in a patch. The addon-resident fallback also needs a generated, removable bridge layout.
- The bridge and its listener die with the map; a map reload was measured to rebuild correctly. A full Dota process restart and a cache eviction still need the same live matrix. The tool distinguishes a cached bridge from a missing one by ping, not by the one-time ready marker.
- The debugger and its console are undocumented engine tools; a patch can rename the window, the command or the JavaScript binding. The script cache is a measured, version-specific behavior, so the console must be re-measured each engine version before relying on it.
- The process-wide one-slot cache makes the debugger fallback fragile: a single stray submission — including a developer's manual `$.Msg(1)` — fills it until the next Dota restart. A tool that relies on the fallback must own the first submission or detect the stale cache and ask for a restart.
- The debugger fallback's listener also dies with the layout context on a map reload; re-arming means submitting once more in a JavaScript-backed context. A tool must handle that cycle or accept a broken fallback after a reload.
- `eval` is blocked, so the bridge depends on the panel method `RunScriptInPanelContext`; a patch can remove or rename it. The debugger bootstrap must also stay under the TextEntry's ~128-character paste limit.
- Automated focus changes can interrupt the user mid-keystroke. `dota_input` keeps the takeover bounded, defaults to leaving the game foreground, and re-shows a hidden game window when an explicit focus restoration hides it.
- Console transport is line-oriented; JSON results need escaping, chunking and a size cap the console can actually carry.
