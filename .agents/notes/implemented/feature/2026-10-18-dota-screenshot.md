# Agent Note: Game screenshot tool

English | [中文](2026-10-18-dota-screenshot.zh.md)

Status: implemented

## Problem

An agent testing an addon cannot see the game. When a map never loads, a phase never advances, or the console stops answering, the only evidence is console text, and live runs have shown that text can be silent about the actual state: a launch that never started, or a team-select screen the addon is waiting on. The developer then has to look at the screen and describe it. A screenshot taken through the engine console does not help in exactly these cases, because it needs a responsive game and a working console connection.

## Decision

`dota_screenshot` returns a game screenshot (see `GLOSSARY.md`): an image of the Dota 2 game window taken from outside the game. Spec: issue #12.

- **Source**: Windows.Graphics.Capture on the game viewport window, the visible top-level `dota2.exe` window titled "Dota 2". Other tools-mode windows are out of scope. The capture never sends the game a message and never uses the console.
- **Background**: the window needs no focus and need not be on top; windows covering it are not captured. Cursor capture and the capture border are turned off where the OS supports it; both properties are set by reflection, because older Windows 10 metadata lacks them and naming them would fail compilation there.
- **Helper**: C# source embedded in the TypeScript module, compiled asynchronously on first use (a cold compile does not block the MCP server) with the .NET Framework `csc.exe` that ships with Windows and cached under `os.tmpdir()/dota2-mcp/capture/<source hash>/`. It references only the GAC facades and the split WinRT metadata in `System32\WinMetadata` that every Windows 10/11 has. The `System.Runtime.WindowsRuntime` await and event helpers need the SDK-only unified `Windows.winmd`, so the helper wraps WinRT async calls itself and polls the free-threaded frame pool instead of subscribing to `FrameArrived`. Each compiler writes its own source and output file and renames into the cache; a session that loses the race uses the cached exe. The repository ships no binary.
- **Persistent cache**: `helper --watch <stateDir> <helperPath>` is a detached singleton shared by every MCP session using that state directory. It starts when the console first connects to Dota or on the first screenshot call. Its atomic `watcher.lock` contains the protocol version, PID, and helper path, and the C# process holds it with `FileShare.Read` for its lifetime. An upgrade compares the path in the same lock instance, stops the old helper, and waits for the lock to be released. A stale lock whose handle is no longer held is quarantined by rename, never used as permission to kill a reused PID. The watcher holds the newest frame delivered by its existing WGC session in memory rather than writing periodic screenshots. It does not recreate sessions on a timer: a new session can replay the same old window image, which must not refresh `captured_at` or clear `stale`. A different Dota window or process resets the cache. With no Dota process and no requests for five minutes, it exits.
- **Protocol**: a request is a four-line `<id>.request` file (`outPath`, `maxWidth`, `format`, `restore`); the helper atomically replaces `<id>.reply` with JSON containing `ok`, `width`, `height`, `hung`, `restored`, `stale`, `captured_at`, or `ok: false` with `error` (`no_window`, `minimized`, `no_frame`, `internal`) and `message`. It writes `{"accepted":true}` before starting work and `{"restoring":true}` before restoring a minimized window. `helper --minimize` remains a one-shot command for cleanup after helper loss. `DOTA2_CAPTURE_HELPER` replaces the helper (a `.js`/`.mjs` path runs under the current node); this is the one seam the offline test replaces. `DOTA2_CAPTURE_DISABLE_WATCHER=1` disables only automatic startup for offline console tests; an explicit screenshot call still starts the watcher.
- **Isolation**: after the helper is available, a request shares a 5 s wall-clock deadline across watcher startup, capture, stop, and re-minimize. Cold compilation is a separate one-time setup phase with its own error. Only an accepted request may stop the watcher on expiry; a request still waiting in the serial queue leaves the healthy shared helper alone. A kill gets a 250 ms grace past the request deadline, because a timeout spends the whole budget; on POSIX a killed child that remains a zombie counts as stopped. The tool waits for lock release (or fake-helper process exit) within that grace, then removes only state still matching the old lock. If the helper had reported `restoring`, both timeout and unexpected-helper-exit paths attempt `helper --minimize` only while budget remains; expiry can therefore leave the window restored, and the result says that re-minimizing was not completed. Old protocol files are discarded or pruned. A failed capture deletes its output file. Helper subprocesses use a credential-scrubbed environment. The tool is not gated on vconsole and works while the relay is disconnected.
- **Hung game**: the watcher returns its newest cached frame immediately when no newer frame arrives. It marks the result `stale: true` when a restored minimized window yields no new frame, when the cached dimensions no longer match the window, or when the cache is over one second old, and always includes `captured_at` so the agent can judge freshness. `hung: true` comes independently from `IsHungAppWindow`. If the watcher has never captured a frame, a sustained hang still produces the hung-specific `no_frame` error; the tool never substitutes a screen capture or an unmarked older image.
- **Minimized window**: with `restore` (default `true`) the helper restores the window with `SW_SHOWNOACTIVATE`, keeps the latest frame that arrives within 300 ms (live, Dota restored without focus renders no new frame, and the frame Windows hands over at once is the window's correct content), captures, and re-minimizes with `SW_SHOWMINNOACTIVE`. A window that is not minimized is captured at once. With `restore: false`, or when the saved video settings say exclusive fullscreen (`setting.fullscreen "1"`), a minimized window is reported instead of restored.
- **Output**: scaled to `max_width` (default 1280), `jpeg` quality 80 by default or `png`, returned as MCP image content plus the saved path. Files go to `os.tmpdir()/dota2-mcp/screenshots/` (`DOTA2_SCREENSHOT_DIR` overrides), keeping the 20 most recent; pruning touches only file names the tool itself generates.
- **No Dota window**: an error; the screen is never captured instead. **Platforms**: Windows only.
- **Other tools**: the shared stuck report mentions `dota_screenshot`; no tool attaches a screenshot automatically.

## Alternatives considered

- **Engine console `screenshot` / `jpeg`.** Rejected: needs a responsive game and a console connection, which are what is missing when a screenshot is most needed.
- **GDI `BitBlt` on the window DC.** Rejected: DirectX windows usually come out black, and covered regions are not captured.
- **`PrintWindow` with `PW_RENDERFULLCONTENT`.** Rejected: it waits on the game's message loop and blocks when the game hangs. A bounded standalone live experiment confirmed that it exceeded its 3 s limit during a hang. Where the WGC helper build fails, the tool returns an error with the compiler output and no screenshot.
- **A fresh WGC session for every call.** Rejected for the tool path: a sustained hang can leave a new session with no frame at all. The persistent session preserves the last good frame instead. The one-shot CLI remains only as a compatibility path and for `--minimize`.
- **Periodic WGC session recreation or `SystemRelativeTime` deduplication.** Rejected: recreation replayed old images as new, and the timestamp could advance even when the encoded images were byte-identical. Freshness therefore comes only from delivery by the current persistent session.
- **Return an older image without freshness metadata.** Rejected: `stale` and `captured_at` make the distinction between a current frame and a cached one explicit.
- **Per-phase timeout budgets.** Rejected: startup, capture, and cleanup can otherwise stack well beyond the promised 5 s. The cold compiler has a separate setup budget because it is a one-time operation.
- **A PID-only watcher lock.** Rejected: Windows can reuse the PID after a crash, so liveness and termination must be tied to the held lock handle, not merely that number.
- **Detect exclusive fullscreen from window styles, monitor bounds, or DWM attributes.** Rejected after live `-fullscreen` and `-noborder` probes: minimized borderless windows can share `WS_POPUP`, non-topmost style, monitor bounds, and DWM values with exclusive windows. The saved `video.txt` setting remains a heuristic, not a reliable runtime detector.
- **DXGI Desktop Duplication.** Rejected: it captures the whole monitor, including windows covering the game.
- **Shipping a prebuilt capture executable.** Rejected: it breaks the no-external-binary rule, and the source build makes it unnecessary.
- **Restoring a minimized window and leaving it restored.** Rejected: re-minimizing returns the desktop to the state the developer left it in.

## Consequences

Bought: one call shows the agent the game screen, about 0.35 s for a fresh capture and about 0.07 s for a cached frame, with no console, vconsole, or focus involved. Once the watcher has captured a frame, a later sustained hang does not depend on Windows producing another one. Cost: Windows only; the first call needs the system `csc.exe`, verified on one Windows 11 machine; one resident helper and its frame memory remain while Dota is active; when Dota stops presenting in the background, results stay `stale` until the existing session delivers again; a restored minimized window flashes briefly; images cost the agent tokens, limited by the default width. A first-ever capture after a long hang can still have no cached frame and fail. A timeout during restoration can leave the window restored, with the result explicitly reporting that cleanup did not finish. The exclusive-fullscreen check reads saved settings, so a mode changed in game but not saved is not seen; the live style/DWM probes did not provide a reliable runtime alternative.

## Testing

- `scripts/test-screenshot.mjs` (offline, runs on Windows and Linux): drives the real MCP server through stdio with `DOTA2_CAPTURE_HELPER` pointing at a fake persistent node helper. It covers helper reuse, image bytes and saved paths, option forwarding, fresh versus cached results, hung and no-cache errors, minimized restoration, accepted-request timeout termination, startup+capture sharing one 5 s deadline, queued-request timeout without termination, incomplete re-minimizing after deadline expiry and successful re-minimizing after early helper loss, protocol-file cleanup, empty-lock recovery, launch failure, exclusive fullscreen, and pruning. Process-exit hooks clean up both MCP-spawned and in-process fake watchers.
- Live (Windows 11, Dota 2 with `-tools`): the system `csc.exe` compiles the helper. A normal MCP console call starts the persistent watcher without an explicit screenshot request. With rendering stopped in the background, repeated captures preserve the original timestamp and remain `stale`; with `r_always_render_all_windows` temporarily enabled for the test, timestamps advance and results are fresh. Three concurrent MCP sessions share one watcher and all receive images. Visible and minimized captures return only the game viewport; the minimized window is restored, captured, and minimized again without changing the foreground window, and `restore: false` leaves it minimized.
- Lifecycle live tests: a real helper killed after its `restoring` progress leaves Dota minimized again, and the next call starts a replacement. A quick Dota process restart returns no old cached image and produces a new frame timestamp in the same watcher. With Dota absent and no requests, the watcher exits after about five minutes (303 s measured); relaunching Dota and capturing starts it on demand. An isolated stale lock containing the caller's own live PID is quarantined without killing that process.
- Live with a bounded Lua busy loop, after the watcher has a cached frame: captures at about 3 s and 8 s both return the correct game viewport in about 0.07–0.09 s. The later result carries `hung: true`, `stale: true`, and the original frame timestamp instead of the previous `no_frame` error. The game finishes its finite loop and subsequent Lua execution succeeds. An isolated real-helper run also placed the caller's own live PID in an unheld stale lock: the lock was quarantined, a new watcher started, and the caller was not killed. The full offline suite also passes beside the live daemon and watcher, leaving their state and PIDs unchanged and no test helpers behind.

Not covered live: reliable runtime exclusive-fullscreen detection, the image WGC returns once Windows swaps in a "not responding" ghost, whether the capture border is hidden, and cache invalidation across a window resize (the current video mode rejected both Win32 and cvar resize attempts). A real timeout while the window is being restored remains covered only by the fake-helper test; the real helper-loss path was verified separately.
