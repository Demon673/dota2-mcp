# Agent Note: Panorama bridge and OS input tools

English | [中文](2026-10-26-panorama-bridge-and-input.zh.md)

Status: implemented

## Problem

The MCP surface could run server Lua and read the VCon console, but it could not inspect or operate the client UI: no panel identity, bounds, visibility or live state, and no way to activate a control without a human. Server Lua has no Panorama access, and the engine's debugger path needs foreground typing plus a process-wide one-slot script cache. The shipped answer had to execute arbitrary JavaScript in a JavaScript-backed Panorama context without editing the addon, and operate the game through real OS input where no background path exists.

## Decision

**Execution path: transient dynamic HUD bridge.** Two source files (layout XML plus an included JS file) ship with the MCP server. Provisioning is copy → engine compile → ready → delete: copy them under `{dota2Path}/content/dota_addons/<addon>/panorama/layout/custom_game/<bridge>/`, call `CustomUI:DynamicHud_Create(PlayerID, ElementID, 'file://{resources}/layout/custom_game/<bridge>/<bridge>.xml', {})`, wait for `MCP_BRIDGE_READY` on `PanoramaScript`, then delete the source copies and both compiled outputs. The client's process-level layout cache keeps the running bridge alive; a map reload destroys the HUD and the next exec rebuilds it; a Dota restart clears the cache and provisioning repeats. The layout path must be resource-relative (`file://{resources}/...`); an absolute path is rejected, and any `..` segment is fatal to the game. The XML includes its script through `<scripts><include .../></scripts>`; the current on-demand compiler rejects an inline `<script />`.

**Protocol and ownership.** The daemon holds a random 128-bit token and a source-hash generation that namespace every event, element id and directory (`d2mcp_<token>_<generation>_exec|ack|ping|pong`). The bridge answers a ping with a pong and an exec with `started` (before compiling) and `done` (after running) acks; acks travel client→server through `GameEvents.SendCustomGameEventToServer` to a server `CustomGameEventManager:RegisterListener`, which prints token-prefixed console lines the tool matches. The Lua VM cannot block on the client VM, so the tool waits on the console marker. Ensure is idempotent: install the listener, ping, reuse a matching pong, try `DynamicHud_Create` from the process cache, and only then copy/compile/delete. A missing `started` is safe to retry; `started` without `done` returns `exec_incomplete` instead of running twice; acks are cached by request id. Invalidation keys on Dota process start, map, addon and generation. Multiple MCP sessions share one bridge manager, one provisioning lock and one ack router; a generation change destroys known old element ids and sweeps only token-named directories. Failure codes: `bridge_unavailable`, `bridge_compile_failed`, `bridge_ping_timeout`, `exec_not_started`, `exec_incomplete`, `js_error`, `lua_listener_failed`; a failed cleanup is a warning, not a bridge failure.

**Tool surface.** `panorama_exec_js` runs short JavaScript (`return <value>`) with the `MCP` helpers: discovery (`map`, `customUi`, `hudElements`, `children`, `top`, `select`, `$`, `context`, `locate`, `panel`, `text`, `cls`, `style`, `visible`, `snap`, `log`, `help`), geometry (`rect`, `center`, `isVisible`, `panelAt`), cursor/world conversion (`cursor`, `entitiesAt`, `worldToScreen`, `screenToWorld`), game state (`units`, `unitInfo`, `selection`, `selectUnit`, `selectAllUnits`, `camera`, `order`), and background events (`dispatch`, `focus`, `blur`, `selectPanel`, `setValue`, `setText`, `on`, `emit`). The bridge runs in its own dynamic HUD layout context: engine globals and methods on reachable panels work; addon-defined globals do not. Native `$` resolves only inside the bridge layout; `MCP.select`/`MCP.$` search from the outermost panel (`MCP.top()`, measured `DotaHud`) with an optional scope. `focus`/`blur` raise `onfocus`/`onblur`, `TogglePanelSelected` is the reliable background `onselect` path, and the value/text setters raise their change events while the game is unfocused; `$.DispatchEvent('onactivate')` and every `onmouse*` name are rejected, so button activation and hover still need real input or an addon test hook. Created panels can live under `MCP.top()` and disappear only after a client render frame; engine panels cannot be reparented. The bridge reaches the HUD top-level window only; sibling top-level windows (dashboard, debugger) have separate contexts and are owned by [the proposal](../../../proposed/feature/2026-10-26-panorama-ui-control.md). A result over ~12 KB returns truncated with a head.

**OS input.** `dota_input` is the window/input path: `window_info` reports outer/client rectangles, client origin, DPI and foreground state; move/click/down/up/drag/wheel, key press/down/up and Unicode text take client-area coordinates; out-of-bounds coordinates fail before input. The game stays foreground by default; the previous foreground window is restored only with `restore_focus:true`, and a requested restoration re-shows a hidden game window without activating it.

## Verification

Live: the copy → compile → ready → delete cycle ran through a content-directory junction and left the repository's git status unchanged; deleting the source and compiled outputs kept the bridge alive (`13579` after deletion); a map reload rebuilt it (`rebuilt:true`, result `42`); a syntax error returned `js_error`; panel text/visible/style round-tripped; a probe Button received real `onactivate` and hover enter/leave; Unicode text and key presses reached the native chat TextEntry; the game window remained available after input; a created panel disappeared only after a client render frame. The debugger bootstrap and the addon-resident and base-game/junction variants were verified during the design and remain fallbacks, not the shipped default.

## Alternatives considered

- **Base-game loose resources or an addon game-directory junction.** Verified fallbacks for a read-only addon or an engine without on-demand source compiling: stage the compiled pair under `{dota2Path}/game/dota/panorama/...` or point a junction there. Rejected as the primary path: base-game staging writes into the Dota install, and a mounted junction is visible to git and must not be committed.
- **Addon-resident bridge.** Verified end to end and kept as an explicit opt-in fallback: a compiled bridge layout lives in the addon. Rejected as the default because it edits addon files the developer owns.
- **Debugger one-slot bootstrap.** Verified end to end and kept as the no-file fallback: the first debugger-console script subscribes to a server event and calls `RunScriptInPanelContext`. Rejected as the primary path because the console needs foreground typing, a JavaScript-backed selected panel and a process-wide one-slot script cache.
- **Writing the bridge into the user's addon as product behavior.** Rejected: it edits source we do not own and contradicts the addon-ownership contract; live experiments used the test addon only.
- **Starting with OS-level automation only.** Kept as the input path, not the inspection path: it gives coordinates and clicks but no panel identity, attributes or styles, and it necessarily takes the input device.
- **Reading debugger output by screenshot and OCR.** Rejected: fragile, slow, and unnecessary when a console or event channel can carry the result.
- **`eval(d.code)` in the bridge.** Rejected by the engine: code generation from strings is blocked; `RunScriptInPanelContext` is the working compile-and-run entry.

## Consequences

Bought: arbitrary JavaScript in a JavaScript-backed Panorama context without addon edits; live panel inspection and operation; background event drivers that work while the game is unfocused; geometry and game-state helpers; one bridge shared by every MCP session; and real OS input where no background path exists.

Cost: the bridge depends on the undocumented `CDOTA_CustomUIManager` API and `RunScriptInPanelContext`, and on the tools-mode on-demand compiler; the process layout cache can serve an old source at the same path, so a bridge revision needs a new path or a fresh Dota process; provisioning writes two source files and two compiled outputs for a short window and a killed process can leave them (the dedicated directory and cleanup sweep bound the damage); fed code is bounded by the `dota_run_lua` statement limit (about 510 bytes wrapped, roughly 300 bytes of Lua); created panels disappear only after a client render frame; the bridge reaches the HUD top-level window only; OS input takes focus for the bounded action; the layout loader treats any `..` segment as fatal, so traversal must never be probed live.

Deferred: debugger inspection readback, multi-root access and the remaining lifecycle matrix are owned by [the proposal](../../../proposed/feature/2026-10-26-panorama-ui-control.md).
